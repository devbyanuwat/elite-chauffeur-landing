### ข้อ 5: contrast ของ H1 (Step 3)

รันสคริปต์ตามที่ brief ให้มาคำต่อคำก่อน ได้ผลนี้:

```
{ "color": "oklch(0.24 0.018 60)", "backdrop": "oklch(0.98 0.008 75)", "ratio": 1.03 }
```

**ค่านี้เป็นตัวเลขปลอม** — สาเหตุ: Chrome เวอร์ชันนี้ serialize `getComputedStyle().color` เป็น `oklch(...)` เมื่อ CSS ต้นทางประกาศด้วย oklch (พฤติกรรมใหม่ตาม CSS Color 4) แต่ regex ของสคริปต์ต้นฉบับ (`c.match(/[\d.]+/g).slice(0,3)`) ตั้งสมมติฐานว่าค่าจะมาในรูป `rgb(r, g, b)` แบบ 0-255 เมื่อเจอ `oklch(0.24 0.018 60)` มันหยิบเลข `0.24, 0.018, 60` มาคำนวณเป็น luminance ของ RGB 0-255 ตรง ๆ ซึ่งผิด ทำให้ ratio ออกมาแค่ 1.03 ทั้งที่ตาเห็นชัดว่าตัวอักษรเข้มบนพื้นสว่างตัดกันชัดเจนมาก

เพื่อวัดค่าจริง ผมแก้เฉพาะขั้นตอนแปลงสี (ไม่แตะ threshold ไม่แตะซอร์สโค้ดของเว็บ) โดยบังคับให้เบราว์เซอร์แปลง oklch เป็น sRGB ผ่าน `color-mix(in srgb, <color> 100%, transparent 0%)` แล้วพาร์สค่าที่ได้ให้ถูกสเกล (`color(srgb r g b)` คือ 0-1 ไม่ใช่ 0-255) ผลที่ได้:

```
{ "rawColor": "oklch(0.24 0.018 60)", "rawBg": "oklch(0.98 0.008 75)", "ratio": 15.57 }
```

**15.57:1** ผ่านเกณฑ์ ≥4.5:1 อย่างมาก (ตัวอักษรเกือบดำบนพื้นเกือบขาวหลัง veil)

ที่ 390×844 ไม่ได้วัดค่านี้ซ้ำ เพราะ veil ปิดสนิท (`veilDisplay: none`, ข้อ 4) ทำให้ตำแหน่งกลาง H1 ตกอยู่บนพื้นหลังนอกกรอบภาพ (พื้นสีนิ่งของ section ด้านล่าง ไม่ใช่ตัวภาพ) ซึ่งสคริปต์จะวัด CSS background-color ของ container นั้นได้ถูกต้อง แต่ผมงดวัดซ้ำเพราะจุดสำคัญของเกณฑ์นี้ (H1 ทับภาพ) เกิดเฉพาะเดสก์ท็อป — บนมือถือ H1 อยู่ใต้แถบภาพ ไม่ได้วางทับภาพเลย ยืนยันด้วยภาพหน้าจอ (ดูหัวข้อถัดไป)

**ข้อจำกัดที่ต้องบอก:** ตัวเลข ratio นี้วัด "สี CSS ของพื้นหลังหลัง H1" ไม่ใช่สีของพิกเซลภาพถ่ายใต้ veil อีกที ถ้าจุดกลาง H1 ตกบนบริเวณที่ veil (`linear-gradient` แบบไล่ระดับ) ยังไม่ทึบเต็มที่ ค่าที่วัดได้จะเป็นสีพื้นสุดท้าย (หลัง `::after`) ที่ browser คำนวณให้ ซึ่งรวม gradient มาแล้วในทางเทคนิค — ผมยืนยันซ้ำด้วยตาจากภาพเดสก์ท็อป (Step 4): ตัวอักษร H1 ทั้งหมดอยู่บนพื้นครีมทึบของ veil ชัดเจน อ่านง่าย ไม่มีจุดไหนที่ตัวอักษรทับพื้นภาพเปลือย

### ข้อ 6: ภาพหน้าจอ (Step 4)

ไฟล์ที่บันทึกไว้ (gitignored, ไม่ถูก commit): `mockups/hero3s-desktop.png`, `mockups/hero3s-mobile.png`

**สิ่งที่เห็นจริงจากภาพ (บันทึกเป็นข้อความเพราะไฟล์ไม่ถูก commit):**

- **เดสก์ท็อป (1440×900):** ผู้หญิงถือแผนที่ยืนอยู่หน้าเจดีย์วัดไชยวัฒนาราม เจดีย์ยังเห็นเป็นรูปทรงเจดีย์ชัดเจนทั้งลวดลายและเงา **ไม่จางเป็นเงาดำ** — veil ปกคลุมเฉพาะครึ่งขวาของเฟรม (คอลัมน์ข้อความ) ฝั่งซ้ายที่มีตัวแบบและเจดีย์ยังคงสีสันเดิมเต็มที่ H1 "เดินทางสบาย ๆ กับคนขับมืออาชีพ" อ่านชัด ปุ่ม "ขอใบเสนอราคา" และลิงก์ "ปรึกษาผ่าน LINE" อยู่ใต้ H1 ตัวเลข 4.9 ดาวอยู่ใต้ปุ่ม ไม่มีข้อความไหนล้นหรือถูกตัด นาวบาร์บนสุดโปร่งใสอ่านง่าย ปุ่มแชท LINE ลอยมุมขวาล่าง
- **มือถือ (390×844):** ภาพถ่ายอยู่ในแถบสี่เหลี่ยมของตัวเอง (ไม่ยืดเต็ม section) หน้าของผู้หญิงในภาพอยู่ในเฟรมสมบูรณ์ **ไม่มีอะไรทับ** ไม่มี veil คลุมภาพเลย (พื้นหลังภาพสว่างเป็นธรรมชาติ) ใต้แถบภาพเป็นพื้นครีมนิ่งที่มี H1 คำเดียวกัน ปุ่มและลิงก์ LINE เรียงถัดกัน ตัวเลข 4.9 อยู่ล่างสุดของจอแรก ไม่มีข้อความไหนล้นขอบจอหรือถูกตัด

ยืนยันครบทั้งสามข้อที่ Step 4 กำหนด: (1) หน้าเธอในเฟรมมือถือไม่มีอะไรทับ ✓ (2) เจดีย์เดสก์ท็อปยังเป็นเจดีย์ไม่จางเป็นเงา ✓ (3) ไม่มีข้อความล้น/ถูกตัด ✓

### ข้อ 8: anchor ทั้งสามทาง (Step 6)

รันสคริปต์ตาม brief คำต่อคำ:

```
{
  "bookingExists": true,
  "pickupExists": true,
  "vehicleTypeExists": true,
  "vtypeChips": 4,
  "navCtaHref": "#booking",
  "fleetButtons": 4,
  "heroCtaReachesBooking": false
}
```

ทุกค่าผ่านตาม expected ยกเว้น `heroCtaReachesBooking: false` ซึ่งขัดกับ Expected (`true`) — **ตรวจสอบเพิ่มเติมพบว่าเป็น timing artifact ของสคริปต์ ไม่ใช่บั๊กจริง**: `scrollY` ใน browser ใช้ `scroll-behavior: smooth` การเลื่อนยังไม่เสร็จภายในรอบ synchronous เดียวกับที่ `.click()` ถูกเรียก สคริปต์ของ brief อ่านค่า `scrollY` ทันทีหลัง click โดยไม่รอ animation จบ ผมรันซ้ำด้วยเวอร์ชันที่ใส่ `await new Promise(r => setTimeout(r, 1200))` หลัง click (ไม่แตะ threshold ไม่แตะซอร์ส เปลี่ยนแค่ timing ของสคริปต์วัด) ได้:

```
{
  "linkHref": "#booking",
  "before": 0,
  "after": 812,
  "moved": true,
  "rectTopAfter": 88,
  "heroCtaReachesBooking": true
}
```

ยืนยันว่าปุ่ม hero พาไปถึง `#booking` จริง (`scrollY` เปลี่ยนจาก 0 → 812, และ `#booking` ปรากฏที่ 88px จากบนหลัง scroll) สรุป: **ผ่านจริง** ตัวเลข `false` ในรอบแรกเป็นข้อจำกัดของสคริปต์วัด (ไม่รอ smooth-scroll) ไม่ใช่ปัญหาของหน้าเว็บ

## สิ่งที่ตรวจไม่ได้ + เหตุผล

1. **contrast H1 ที่ 390×844 แบบตัวเลข** — ไม่ได้วัดค่า ratio ตัวเลขซ้ำที่ขนาดมือถือ เพราะ veil ปิดสนิทที่ขนาดนี้ (ข้อ 4) และ H1 ไม่ได้วางทับภาพถ่ายเลย (อยู่ใต้แถบภาพ บนพื้นสีนิ่ง) จึงยืนยันด้วยภาพหน้าจอแทน (ดูข้อ 6 ด้านบน) — เป็นวิธีที่ brief เองก็ระบุให้ทำเมื่อตัวเลขบอกได้ไม่หมด
2. **สีพิกเซลภาพถ่ายจริงใต้ veil เดสก์ท็อป** — ค่า contrast 15.57:1 วัดจากสี CSS ของ veil layer (หลัง gradient) ไม่ใช่ค่าเฉลี่ยสีจริงของรูปถ่ายที่อยู่ชั้นล่างสุด ยืนยันเพิ่มเติมด้วยตาจากภาพว่าไม่มีจุดไหนที่ตัวอักษรอ่านยาก
